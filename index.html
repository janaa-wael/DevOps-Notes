Previous-session recap

The session began by reviewing IAM, basic networking, VPC components, and the first EC2 deployment.

IAM concepts reviewed

IAM user

A long-lived identity generally created for a person or application that needs AWS permissions.

IAM group

A collection of IAM users. Permissions assigned to the group are inherited by its members.

IAM role

A temporary identity assumed by a user, service, or workload without embedding permanent credentials.

Ways to interact with AWS

  • AWS Management Console: browser-based access using a username and password.
  • AWS CLI: command-line access, usually authenticated using credentials or a role.
  • AWS APIs and SDKs: application code can create and manage resources programmatically.
  • Infrastructure as Code: tools such as Terraform, AWS CloudFormation, or custom Python code can provision infrastructure.
Security principle Avoid storing long-lived access keys inside EC2 instances, source code, shell history, or configuration files. Prefer IAM roles and temporary credentials.

Networking foundations

What is a network?

A network is a group of connected devices that can communicate and share resources. Every device needs an identifier so traffic can be delivered to the correct destination. In IP networking, that identifier is an IP address.

IP addresses, DNS, and ports

IP address

The address used to identify a network interface. The instructor compared it to the address of a building that a delivery driver uses to reach a destination.

DNS

Converts human-readable names into IP addresses. It is easier to remember a domain name than a numeric IP. Common records include A, AAAA, and CNAME.

Port

Identifies a service on a host. The server is the building; ports are the individual apartments or channels. Examples include HTTP on port 80 and HTTPS on port 443.

IPv4 and CIDR notation

IPv4 contains 32 bits, normally written as four decimal octets. A CIDR prefix such as /16 or /24 tells us how many leading bits belong to the network portion.

CIDR Network bits Host bits Example interpretation
10.0.0.0/16 16 16 Addresses begin with the same first two octets inside this network.
10.0.1.0/24 24 8 Addresses begin with 10.0.1; the final octet identifies hosts.
10.0.1.0/27 27 5 A smaller subnet contained inside a larger parent CIDR block.
Subnetting rule A child subnet must fit inside its parent VPC CIDR and must not overlap another subnet. A larger prefix number means a smaller network. For example, a /27 subnet can fit inside a /24 network.
AWS-specific correction The lecture simplified address reservation as “the first and last address.” In an AWS subnet, AWS reserves the first four IP addresses and the last IP address.

Moving traffic between networks

Traffic between separate networks needs a routing device or routing service. A route table provides directions: it maps a destination CIDR to a target such as a local route, Internet Gateway, NAT Gateway, peering connection, Transit Gateway, or VPC endpoint.

03

VPC architecture

Virtual Private Cloud

An Amazon VPC is an isolated virtual network inside AWS. It is the main boundary in which subnets, route tables, network interfaces, gateways, and compute resources are organised.

Why divide a VPC into subnets?

A VPC is a large network. Subnets segment it into smaller networks, normally distributed across Availability Zones. The instructor compared a VPC to a large residential building and subnets to separate apartments.

High availability

A production architecture should normally use more than one Availability Zone. If one zone or instance fails, another zone can continue serving the application.

Public versus private subnet

Property Public subnet Private subnet
Default route Usually 0.0.0.0/0 → Internet Gateway No direct route to an Internet Gateway
Public IP An instance may receive one Normally disabled
Inbound internet access Possible when routing and security rules allow it Not directly reachable from the internet
Typical workloads Load balancer, bastion host, NAT Gateway Application servers, databases, Kubernetes worker nodes
Important distinction A subnet is not public merely because an EC2 instance has a public IP. The subnet needs a route to an Internet Gateway, and the instance must have a usable public address and permissive security controls.

Security group versus network ACL

Feature Security group Network ACL
Scope Attached to a network interface or resource Applied at subnet level
State Stateful Stateless
Rules Allow rules only Allow and deny rules
Return traffic Automatically allowed for an established flow Must be explicitly permitted in the opposite direction
Evaluation All relevant rules are evaluated Rules are processed from the lowest rule number; the first match wins

Lab: Build the VPC

The instructor rebuilt the architecture using the VPC creation workflow that creates several components in one operation.

Target architecture

Two-AZ VPC layout
Public subnet — AZ A
Private subnet — AZ A
VPC
CIDR: 10.0.0.0/16
Public subnet — AZ B
Private subnet — AZ B

Configuration used in the demonstration

  1. Create one VPC with an appropriate CIDR block, such as 10.0.0.0/16.
  2. Select two Availability Zones.
  3. Create two public subnets and two private subnets.
  4. Use non-overlapping subnet CIDRs, commonly /24 blocks inside the /16 VPC.
  5. Enable DNS hostnames and DNS resolution.
  6. Create and attach an Internet Gateway.
  7. Create route tables and associate the correct subnets.
  8. Do not create the NAT Gateway yet; it is added later to demonstrate the difference.
  9. Do not create a VPC endpoint yet; it is added later to demonstrate private S3 access.

What the resource map creates

  • The VPC and its CIDR.
  • Public and private subnets.
  • A public route table pointing to the Internet Gateway.
  • Private route tables containing only the local route at first.
  • Subnet associations.
  • An Internet Gateway attached to the VPC.
Resource-map lesson The VPC wizard can create the architecture “in one shot,” but understanding the individual components remains important because troubleshooting requires knowing how each route and association works.

Lab: Public and private EC2 instances

Public EC2 instance

  1. Launch an Amazon Linux instance.
  2. Place it in one of the public subnets.
  3. Enable automatic public IPv4 assignment.
  4. Create or select a key pair.
  5. Create a public security group.
  6. Allow SSH only from a trusted source, not from the entire internet in production.
  7. Allow HTTP port 80 when testing the web server.
  8. Add a user-data script to install and start a web server.
EC2 user data — Amazon Linux 2023 
#!/bin/bash
dnf update -y
dnf install -y httpd
systemctl enable --now httpd

cat > /var/www/html/index.html <<'EOF'
<h1>AWS Networking Lab</h1>
<p>The public EC2 web server is running.</p>
EOF

The first line is the shebang. It tells the operating system which interpreter should execute the script. It becomes especially important when the script uses syntax specific to Bash or another shell.

Amazon Linux 2 note On Amazon Linux 2, use yum instead of dnf.

Private EC2 instance

  1. Launch another Amazon Linux instance.
  2. Place it in a private subnet.
  3. Disable public IP assignment.
  4. Create a separate private-instance security group.
  5. Allow SSH from the bastion security group or the bastion private IP, not from everywhere.
  6. Use the same web-server user-data script to test whether package installation can reach the internet.

Expected result before NAT is configured

  • The public instance can reach the internet and install packages.
  • The private instance has no public IP and cannot be reached directly from the laptop.
  • The private instance also cannot download packages because its route table has no outbound internet path.

Checking the instance

  • Use the EC2 system log and console output to inspect cloud-init and user-data execution.
  • Use the instance screenshot when boot problems are suspected.
  • After connecting, check the service with systemctl status httpd.

Bastion host and Session Manager

Why direct SSH fails

A private EC2 instance has only a private IP and no internet-routable address. A laptop on the public internet therefore cannot open a direct SSH connection to it.

Bastion or jump host

A bastion host is a carefully secured public instance used as an entry point into private networks. The session demonstrated the following path:

Bastion access path
Administrator laptop
→
Public EC2 bastion
Private EC2 workload
Fix private-key permissions 
chmod 400 lab-key.pem
Connect to the public bastion 
ssh -i lab-key.pem ec2-user@BASTION_PUBLIC_IP
Preferred one-command jump using ProxyJump 
ssh -i lab-key.pem \
  -J ec2-user@BASTION_PUBLIC_IP \
  ec2-user@PRIVATE_INSTANCE_IP
Do not copy private keys to the bastion in production The session copied the key file to the public host for demonstration. A safer pattern is SSH ProxyJump, SSH agent forwarding with care, certificate-based SSH, or AWS Systems Manager Session Manager.

Systems Manager Session Manager

Session Manager is a better alternative when configured correctly. It can provide shell access without opening inbound SSH or maintaining a public bastion.

Typical requirements

  • SSM Agent installed and running on the instance.
  • An IAM instance role containing the required Systems Manager permissions.
  • Network access to Systems Manager endpoints, either through NAT/internet or interface VPC endpoints.
  • The instance registered as a managed node.
07

NAT Gateway

The problem NAT solves

Production workloads are often deployed in private subnets. They still need outbound access for package updates, container image downloads, third-party APIs, monitoring agents, and operating-system maintenance. They should be able to initiate connections outward without becoming directly reachable from the internet.

Network Address Translation

NAT maps private source addresses to a public address for outbound communication. Return traffic for those initiated connections is sent back to the private workload, but unsolicited inbound internet connections are not forwarded to it.

Private subnet egress through NAT
Private EC2
Private Kubernetes nodes
→
NAT Gateway in public subnet
Internet Gateway → Internet

Configuration steps

  1. Create a NAT Gateway in a public subnet.
  2. Allocate and associate an Elastic IP.
  3. Wait until the NAT Gateway becomes available.
  4. Edit each private-subnet route table.
  5. Add 0.0.0.0/0 → NAT Gateway.
  6. Verify that the public subnet route table contains 0.0.0.0/0 → Internet Gateway.
  7. Retry package installation or an outbound request from the private instance.
Test outbound access from the private instance 
curl -I https://example.com
sudo dnf update -y
ping -c 4 8.8.8.8

After the private route table pointed to the NAT Gateway, package downloads succeeded and the instance could reach the internet while remaining unreachable directly from outside.

Stable outbound IP use case

A third-party vendor may require an allowlisted source IP, for example an SMS provider or external API. Private workloads can exit through the NAT Gateway’s Elastic IP, allowing the vendor to permit one known public address.

NAT Gateway versus NAT instance

Area NAT Gateway NAT instance
Management AWS-managed service You manage the EC2 instance, patches, scaling, and failover
Availability Managed within an Availability Zone Depends on the architecture you build
Customisation Limited Highly customisable
Typical reason to use Standard AWS production egress Unsupported cloud platform, custom routing, or special cost/design requirements
Cost awareness NAT Gateways, public IPv4 addresses, data processing, and cross-AZ traffic can create significant charges. Design one NAT Gateway per Availability Zone for resilient production environments, then evaluate the cost.

VPC peering

Purpose

VPC peering creates private connectivity between two VPCs. Resources can communicate using private IP addresses as though the VPCs were connected networks.

Possible relationships

  • Two VPCs in the same account and Region.
  • Two VPCs in different accounts.
  • Two VPCs in different Regions.
  • Different accounts and different Regions.

Main requirement: non-overlapping CIDR blocks

The address spaces must not overlap. A router cannot make an unambiguous decision if the same destination IP could exist in both VPCs.

Valid

VPC A: 10.0.0.0/16

VPC B: 10.1.0.0/16

Invalid

VPC A: 10.0.0.0/16

VPC B: 10.0.0.0/16

Peering is not transitive

Suppose A is peered with B, and B is peered with C. A cannot automatically reach C through B. A direct A-to-C peering connection is required, or the architecture should use a transit service such as Transit Gateway.

Non-transitive peering
VPC A
A ↔ B ↔ C does not mean A ↔ C
VPC C

Peering configuration steps

  1. Create a peering request from the requester VPC.
  2. Select the accepter account, Region, and VPC.
  3. Accept the request from the accepter side.
  4. Add routes in the requester subnet route tables: destination is the accepter CIDR, target is the peering connection.
  5. Add reciprocal routes in the accepter subnet route tables.
  6. Confirm that the relevant route tables are actually associated with the subnets.
  7. Allow the required protocol and ports in security groups.
  8. Confirm that network ACLs permit traffic in both directions.

Demo failure and troubleshooting

The initial peering connection became active, but ping still failed. The instructor checked security groups and NACLs, then discovered that the required peering routes and subnet route-table associations were missing. After adding the destination CIDRs, selecting the peering connection as the target, and associating the route tables with the correct subnets, traffic succeeded.

Core lesson An active peering connection is not enough. Both sides need correct routes, route-table associations, and security rules.

Why full-mesh peering does not scale

To fully connect n VPCs using pairwise peering, the number of connections is:

Full-mesh peering formula 
connections = n × (n - 1) / 2

For 4 VPCs: 4 × 3 / 2 = 6 connections
For 10 VPCs: 10 × 9 / 2 = 45 connections

AWS Transit Gateway

Why it exists

Transit Gateway acts as a central network hub. Instead of building a large mesh of individual peerings, each VPC attaches to the Transit Gateway.

Hub-and-spoke connectivity
VPC A
VPC B
Transit Gateway
VPC C
On-premises / VPN

Use cases

  • Connect many VPCs using hub-and-spoke routing.
  • Connect VPCs to an on-premises network.
  • Integrate with site-to-site VPN.
  • Centralise shared services, egress, or inspection networks.
  • Share one Transit Gateway across multiple AWS accounts.

High-level workflow

  1. Create the Transit Gateway.
  2. Create a VPC attachment for each VPC.
  3. Select the subnets in each VPC that will participate.
  4. Configure Transit Gateway route tables, associations, and propagations.
  5. Add VPC subnet routes that point remote CIDRs to the Transit Gateway.
  6. Allow traffic in security groups and NACLs.
  7. For cross-account designs, share the Transit Gateway using AWS Resource Access Manager.
Address planning still matters Transit Gateway does not remove the need for unique, non-overlapping CIDR ranges.

When to choose peering or Transit Gateway

Scenario Usually simpler choice
Only two VPCs need direct private communication VPC peering
Many VPCs need transitive routing Transit Gateway
On-premises, VPN, and multiple VPCs must meet at one hub Transit Gateway
Small lab and minimal architecture VPC peering may be enough

VPC endpoints and private AWS service access

The problem

An EC2 instance in a private subnet may need to access Amazon S3, DynamoDB, Systems Manager, CloudWatch, or another AWS service. Without a VPC endpoint, the request may need NAT and a public service endpoint even though both resources are inside AWS.

VPC endpoint idea

A VPC endpoint provides private connectivity from a VPC to a supported service. Traffic remains on AWS networking rather than requiring a public-internet path.

Gateway endpoints

  • Used for Amazon S3 and DynamoDB.
  • Implemented by adding service prefix-list routes to selected route tables.
  • No endpoint ENI is created in the subnet.
  • The session described gateway endpoints as having no additional endpoint charge; always verify current pricing.
  • Endpoint policies can restrict allowed services, actions, buckets, tables, principals, or resources.

Interface endpoints

  • Used by many AWS services, including Systems Manager and CloudWatch.
  • Powered by AWS PrivateLink.
  • Create elastic network interfaces with private IP addresses in selected subnets.
  • Use security groups to control traffic to the endpoint ENIs.
  • Normally support private DNS so standard service hostnames resolve to private endpoint addresses.
  • Usually have hourly and data-processing charges.
Feature Gateway endpoint Interface endpoint
Services S3 and DynamoDB Many AWS and partner services
Implementation Route-table entry ENIs with private IP addresses
Security groups Not attached to the endpoint Attached to endpoint ENIs
Common policy controls Endpoint policy, IAM policy, resource policy Endpoint policy, IAM policy, security groups, resource policy

S3 gateway endpoint demonstration

  1. Attach an IAM role to the EC2 instance so it can call S3.
  2. From the private instance, run aws s3 ls.
  3. While the private subnet still has NAT, the command succeeds through the public S3 endpoint.
  4. Delete or remove the NAT path.
  5. The private instance can no longer reach S3 through the public endpoint.
  6. Create an S3 VPC gateway endpoint.
  7. Select the VPC and associate the endpoint with the private route tables.
  8. Choose a full-access endpoint policy for the first test, then tighten it later.
  9. Run aws s3 ls again.
  10. The command succeeds even though the private subnet has no NAT route, proving that the path is private.
What proved the connection was private? After NAT access was removed, S3 access failed. It worked again only after the S3 gateway endpoint and route-table associations were created.

Policy layers involved

  • IAM identity policy: what the EC2 role is allowed to do.
  • Endpoint policy: what traffic the endpoint permits.
  • Bucket or resource policy: what the target resource accepts.
  • Security group: required for interface endpoints, not gateway endpoints.
  • Route table: required for gateway endpoint traffic.

Attach an IAM role to EC2

Initial error

Running aws s3 ls from the instance failed because the instance had no AWS credentials or attached permissions.

Recommended solution

  1. Create an IAM role whose trusted entity is the EC2 service.
  2. Attach only the permissions required by the workload.
  3. For the demo, an S3 full-access managed policy was used.
  4. Attach the role to the EC2 instance through the instance profile.
  5. Retry the AWS CLI command.
Verify the EC2 role and S3 access 
aws sts get-caller-identity
aws s3 ls

Why the role is better than aws configure

  • No permanent access key is written to the instance.
  • Credentials are temporary and rotated automatically.
  • Permissions can be controlled centrally.
  • The role can follow least-privilege design.
  • Compromising the host does not expose an IAM user’s long-lived secret key.
Least privilege S3 full access was useful for a short demonstration but is excessive for production. Restrict the role to the exact actions and bucket paths that the application needs.

Troubleshooting workflow

The instructor repeatedly emphasised checking the network layer by layer instead of changing random settings.

General connectivity checklist

  1. Addressing: Is the destination IP correct? Do CIDR blocks overlap?
  2. Resource state: Is the EC2 instance, gateway, endpoint, or peering connection available?
  3. Route table: Does the source subnet have a route to the destination?
  4. Reverse path: Can the response return to the source?
  5. Association: Is the intended route table associated with the actual subnet?
  6. Security group: Is the protocol and port allowed?
  7. NACL: Are inbound, outbound, and ephemeral return ports allowed?
  8. Operating system: Is the service running and listening on the expected interface and port?
  9. DNS: Does the name resolve to the correct public or private address?
  10. IAM: Does the caller have permission to access the AWS service?
  11. Endpoint policy: Does the endpoint permit the action and resource?

When ping fails across VPC peering

  • Confirm that the peering request is active.
  • Confirm that CIDRs do not overlap.
  • Add routes on both sides.
  • Associate the route tables with the correct subnets.
  • Allow ICMP in the destination security group.
  • Check NACL rules in both directions.
  • Verify that the instance operating system accepts ICMP.

When a private instance cannot install packages

  • Check that a NAT Gateway exists and is available.
  • Confirm that the NAT Gateway is in a public subnet.
  • Confirm that the NAT Gateway has an Elastic IP.
  • Check 0.0.0.0/0 → NAT Gateway in the private route table.
  • Check 0.0.0.0/0 → Internet Gateway in the NAT subnet route table.
  • Check DNS support, DNS hostnames, NACLs, and outbound security-group rules.

When S3 access fails from private EC2

  • Run aws sts get-caller-identity to verify credentials.
  • Check the EC2 IAM role policy.
  • Check the bucket policy.
  • Check whether NAT is available when using the public S3 endpoint.
  • For a gateway endpoint, confirm route-table associations and endpoint policy.
  • For an interface endpoint, confirm endpoint ENIs, private DNS, and security groups.

Useful commands

Linux and AWS connectivity diagnostics

Practice lab

The instructor recommended learning by doing, revisiting difficult concepts several times, and building a lab for every session. This practice plan converts the session into a repeatable exercise.

Build

  • Create a VPC with a /16 CIDR.
  • Create two public and two private subnets in two Availability Zones.
  • Create and attach an Internet Gateway.
  • Create public and private route tables and make the correct subnet associations.
  • Launch one public EC2 instance and one private EC2 instance.
  • Install a web server using EC2 user data.
  • Connect to the private instance through a bastion host.
  • Replace bastion access with Session Manager.
  • Create a NAT Gateway and confirm private outbound access.
  • Create a second non-overlapping VPC and configure VPC peering.
  • Add routes on both sides and verify private-IP connectivity.
  • Remove NAT access from a private subnet.
  • Attach an EC2 IAM role with limited S3 read permissions.
  • Create an S3 gateway endpoint and confirm private access.

Break and repair

  • Remove the peering route from one side and observe the failure.
  • Associate the wrong route table with a subnet and diagnose it.
  • Block ICMP in the security group and compare it with an NACL failure.
  • Remove the NAT route and observe package-manager failure.
  • Remove the endpoint route-table association and observe S3 failure.
  • Deny access in the endpoint policy and compare the error with a routing timeout.

Key takeaways

  1. A VPC is an isolated network; subnets divide it into smaller address ranges.
  2. Public and private behaviour is primarily controlled by routing, addressing, and security rules.
  3. Security groups are stateful and resource-level; NACLs are stateless and subnet-level.
  4. A bastion host provides a jump path to private resources, but Session Manager is often safer.
  5. A NAT Gateway gives private workloads outbound internet access without direct inbound exposure.
  6. VPC peering connects exactly two VPCs and is not transitive.
  7. Peering requires non-overlapping CIDRs, routes on both sides, and correct security rules.
  8. Transit Gateway scales hub-and-spoke connectivity across many VPCs and hybrid networks.
  9. VPC endpoints allow private access to supported AWS services.
  10. S3 and DynamoDB use gateway endpoints; many other AWS services use interface endpoints.
  11. IAM roles are safer than placing access keys on EC2 instances.
  12. Hands-on troubleshooting is essential; an “active” AWS resource does not guarantee end-to-end connectivity.
