Start with the problem

CI/CD foundations

Jenkins makes more sense after you understand the delivery process it is automating.

CI

Continuous Integration

Developers integrate changes frequently. Each change is automatically compiled, tested, and validated so integration problems appear early.

CD

Continuous Delivery

The application remains releasable. The pipeline prepares and verifies a release, while production deployment usually requires an approval.

CD

Continuous Deployment

Every change that passes the automated checks can move to production automatically, with no manual release gate.

Commit
Checkout
Build
Test
Scan
Package
Deploy
Verify

Why automate?

  • Faster feedback after every change.
  • Repeatable builds and deployments.
  • Fewer manual mistakes and hidden steps.
  • Clear evidence: logs, reports, artifacts, image tags, and rollout status.

DevOps is larger than Jenkins

DevOps combines culture, process, and tools. Jenkins is one orchestrator inside that system; Git stores source, build tools compile it, test tools validate it, registries store packages, and runtime platforms operate it.

02
The mental model

What Jenkins actually does

Jenkins is an automation server that coordinates tools, executes workflows, and records evidence.

Orchestration

Run jobs, place work in a queue, assign it to agents, execute stages in order, and control success or failure paths.

Integration

Connect source control, build tools, test frameworks, scanners, registries, notification systems, and deployment platforms.

Evidence

Keep console logs, test reports, artifacts, pipeline status, metadata, and links that explain exactly what happened.

!
Jenkins does not replace your tools.

Maven still builds Java, npm still builds Node.js, Docker still builds images, and kubectl still talks to Kubernetes. Jenkins decides when and where those tools run.

TermMeaningExample
Job / ProjectA configured unit of automation.A Freestyle job or Pipeline project.
BuildOne execution of a job.Build #42 of java-ci.
StageA visible phase with one clear purpose.Build, Test, Scan, Deploy.
StepAn operation inside a stage.sh 'mvn test'.
ArtifactA build output retained for later use.JAR, ZIP, report, metadata file.
PluginAn extension that adds integrations or functionality.Git, Pipeline, JUnit, Role Strategy.
03
Distributed builds

Controller and agents

The controller manages Jenkins. Agents provide the environments where builds actually run.

Controller responsibilities

  • Host the web UI and API.
  • Store job configuration and credentials.
  • Maintain the build queue and schedule work.
  • Load plugins, manage permissions, and show results.
×
Avoid heavy builds on the controller

In a stronger setup, set controller executors to zero and run builds on agents.

Agent responsibilities

  • Provide a workspace and executors.
  • Run Pipeline steps and Freestyle commands.
  • Provide required tools such as JDK, Maven, Docker, or kubectl.
  • Be static, containerized, or dynamically created.
1. Event arrives

A user clicks Build Now, a schedule fires, or GitHub sends a webhook.

2. Controller queues the build

Jenkins checks job rules, parameters, labels, and available executors.

3. Jenkins allocates an agent

The selected node must match the requested label and have a free executor.

4. Steps run in a workspace

Source is checked out and tools operate on the workspace files.

5. Results return to Jenkins

Logs, reports, artifacts, and final status become visible in the UI.

Node

A machine, VM, container, or pod registered in Jenkins.

Executor

A slot that can run one unit of work. More is not always better.

Workspace

The directory used by a particular job execution on an agent.

Label

A capability tag such as linux, maven, or docker.

Install and unlock Jenkins

For a learning environment, Docker gives you a clean, repeatable Jenkins controller with persistent storage.

✓
Prerequisites

Install Docker and Git on your Ubuntu VM. Run docker --version and git --version before continuing.

Option A — Simple Docker installation

  Terminal
docker volume create jenkins_home

docker run -d \
  --name jenkins \
  --restart=unless-stopped \
  -p 8080:8080 \

A course or demo repository may pin another supported tag, such as lts-jdk17. Use the repository’s exact tag when reproducing that lab; otherwise verify the currently supported Java version before choosing an image tag.

Access control

Users, roles, and folders

Authentication answers “Who are you?” Authorization answers “What are you allowed to do?”

Authentication

Jenkins verifies identity through its own user database or an external identity system such as LDAP, Active Directory, or an SSO provider.

Authorization

Permissions decide who can read, build, configure, create, or delete jobs. The Role-Based Authorization Strategy plugin adds reusable global, item, and agent roles.

Lab: create users and folder-specific roles

Install the plugin

Manage Jenkins → Plugins → Available plugins → search for “Role-Based Authorization Strategy” → Install.

Create users

Manage Jenkins → Users → Create User. Create dev-user and test-user.

Enable role-based authorization

Manage Jenkins → Security → Authorization → Role-Based Strategy → Save.

Create folders

Dashboard → New Item → Folder. Create development and testing.

Define roles

Manage Jenkins → Manage and Assign Roles → Manage Roles.

Assign users

Open Assign Roles and map each user to the intended global and item roles.

Role typeRolePatternMinimum permissionsAssign to
Globalauthenticated-read—Overall / Readdev-user, test-user
Itemdevelopment-read^development(/.*)?$Item / Readdev-user
Itemtesting-delete^testing(/.*)?$Item / Read, Item / Deletetest-user
!
Protect your admin access.

Configure and test new roles in a second browser session before logging out of the administrator account. A wrong security configuration can lock you out.

06
Secure integrations

Credentials, tools, and plugins

Jenkins needs access to external systems, but secrets must never be hard-coded in a job or repository.

U/P

Username + password

Docker Hub login, basic authentication, and some package registries.

TXT

Secret text

Personal access tokens, API keys, webhook secrets, and scanner tokens.

KEY

SSH private key

SSH-based agent connections, private Git servers, and remote deployments.

FILE

Secret file

Kubernetes kubeconfig files, service-account files, and certificates.

ID

Credential ID

A safe reference such as dockerhub-creds; it is not the secret itself.

↻

Rotation

Use dedicated machine credentials, limit scope, and replace tokens before or when they expire.

Add a credential

Manage Jenkins → Credentials → System → Global credentials → Add Credentials

Choose the correct type, enter the secret, assign a clear ID, and add a useful description. Prefer folder-scoped credentials for team-specific applications instead of making every secret globally visible.

Use Docker Hub credentials safely

Jenkinsfile
withCredentials([usernamePassword(
  credentialsId: 'dockerhub-creds',
  usernameVariable: 'DOCKER_USER',
  passwordVariable: 'DOCKER_PASS'
)]) {
  sh '''
    set +x
    echo "$DOCKER_PASS" | docker login \
      -u "$DOCKER_USER" --password-stdin
  '''
}

Global tools

Manage Jenkins → Tools can define named JDK, Maven, Gradle, Git, and Node.js installations. Pipeline names must match the names configured in Jenkins.

Plugins

Install only what the platform needs. Common examples include Pipeline, Git, GitHub Branch Source, Credentials Binding, JUnit, Docker Pipeline, Kubernetes, and Role Strategy.

!
GitHub cannot call your VM’s localhost.

A webhook pointing to http://localhost:8080/github-webhook/ only refers to GitHub’s own machine, not yours. For a local lab, trigger builds manually, poll SCM, or expose Jenkins through a controlled public endpoint. In a hosted environment, use the externally reachable Jenkins URL.

09
Pipeline as code

Pipeline and Jenkinsfile

A Jenkinsfile stores the delivery workflow beside the application, so pipeline changes are versioned, reviewed, and reproducible.

Freestyle

Configured mainly in the UI. Easy for simple tasks, but changes are harder to review and copy between environments.

Pipeline

Defined as code. Supports stages, conditions, parameters, parallel work, approvals, post actions, and reuse.

Minimal Declarative Pipeline

Jenkinsfile
pipeline {
  agent any

  stages {
    stage('Build') {
      steps {
        sh 'ls -ltr'
      }
    }
  }

  post {
    always {
      echo 'Pipeline finished'
    }
  }
}

agent

Where the whole pipeline or a particular stage runs.

stages

The ordered container for visible delivery phases.

steps

The actual commands and Jenkins operations.

environment

Non-secret variables or credential bindings.

parameters

User inputs supplied when a build starts.

post

Actions for success, failure, unstable, or always.

Java CI pipeline

Jenkinsfile — Java/Maven
pipeline {
  agent { label 'linux && maven' }

  environment {
    APP_NAME = 'jenkins-java-demo'
  }

  parameters {
    string(name: 'VERSION', defaultValue: '1.0.0')
    choice(name: 'ENV', choices: ['dev', 'test', 'prod'])
    booleanParam(name: 'RUN_TESTS', defaultValue: true)
  }

  options {
    timeout(time: 20, unit: 'MINUTES')
    timestamps()
  }

  stages {
    stage('Checkout') {
      steps { checkout scm }
    }

    stage('Build') {
      steps { sh 'mvn -B clean package -DskipTests' }
    }

    stage('Unit Test') {
      when { expression { params.RUN_TESTS } }
      steps { sh 'mvn -B test' }
      post {
        always { junit 'target/surefire-reports/*.xml' }
      }
    }

    stage('Package') {
      steps {
        sh 'mkdir -p dist && cp target/*.jar dist/'
      }
    }

    stage('Archive') {
      steps {
        archiveArtifacts artifacts: 'dist/*.jar', fingerprint: true
      }
    }

    stage('Approval') {
      when {
        allOf {
          branch 'main'
          expression { params.ENV == 'prod' }
        }
      }
      steps { input message: 'Deploy to Production?' }
    }
  }

  post {
    success { echo "${env.JOB_NAME} #${env.BUILD_NUMBER} succeeded" }
    failure { echo 'Open the failed stage and inspect Console Output' }
    always  { echo "Result: ${currentBuild.currentResult}" }
  }
}
Node.js CI example
Jenkinsfile — Node.js
pipeline {
  agent { label 'linux && nodejs' }

  stages {
    stage('Checkout') {
      steps { checkout scm }
    }
    stage('Install') {
      steps { sh 'npm ci' }
    }
    stage('Test') {
      steps { sh 'npm test' }
    }
    stage('Build') {
      steps { sh 'npm run build' }
    }
    stage('Archive') {
      steps { archiveArtifacts artifacts: 'dist/**', fingerprint: true }
    }
  }
}
10
Clean build environments

Agents and Docker-based builds

Agents isolate build tools from the controller and let Jenkins route each workload to a suitable environment.

Inbound agent

The agent connects to the controller using a secret, often over WebSocket. Useful for containers, Windows, and restricted networks.

SSH agent

The controller connects to a static Linux host using an SSH credential.

Dynamic agent

Jenkins creates a container or Kubernetes pod for a build and removes it afterward.

Classroom Docker agent workflow

Create the node

Manage Jenkins → Nodes → New Node → Permanent Agent.

Configure it

One executor, remote root /home/jenkins/agent, labels docker linux maven slave, inbound launch method.

Copy the secret

Open the node page and copy only the secret from the generated agent command.

Build the image

The repository’s agent/Dockerfile installs Java, Maven, Git, and Bash.

Run the container

The container joins the controller’s Docker network and starts the inbound agent.

Build and run the demo agent
cd Jenkins-demo
export DEMO_DIR="$(pwd)"

docker network create jenkins-net 2>/dev/null || true

docker build -t jenkins-maven-agent:demo ./agent

docker run -d \
  --name jenkins-slave-1 \
  --network jenkins-net \
  -v "$DEMO_DIR/java-demo-app:$DEMO_DIR/java-demo-app" \
  jenkins-maven-agent:demo \
  -url http://jenkins-master:8080 \
  -secret PASTE_SECRET_HERE \
  -name docker-slave-1 \
  -webSocket \
  -workDir /home/jenkins/agent
!
The command above assumes the controller is also a container named jenkins-master on jenkins-net.

If your controller is installed directly on Ubuntu instead, the connection URL and network approach are different. Do not blindly mix both installation models.

Run a job only on the correct agent

Label expression
pipeline {
  agent { label 'docker && linux && maven' }
  stages {
    stage('Verify Agent') {
      steps {
        sh 'echo $NODE_NAME && java -version && mvn -version'
      }
    }
  }
}

Branch-aware CI

Multibranch Pipeline

Jenkins scans a repository, finds branches and pull requests containing a Jenkinsfile, and creates a child job for each one.

Repository
Branch scan
main job
feature job
PR job

Why use it?

  • No manual job for every branch.
  • Pull-request validation before merge.
  • Branch-specific status and history.
  • Automatic cleanup rules for deleted branches.

Create it

  1. Dashboard → New Item → Multibranch Pipeline.
  2. Add a Git or GitHub branch source.
  3. Enter the repository and credentials.
  4. Set Script Path to Jenkinsfile.
  5. Save and run “Scan Multibranch Pipeline Now”.

Common branch policy

SourceSuggested stagesPurpose
feature/*Build + Unit TestFast developer feedback.
Pull requestBuild + Test + ScanValidate before merge.
mainPackage + Build image + PushCreate a releasable artifact.
release/*Deploy to stagingRelease verification.
TagPublish immutable releaseTraceable production release.
Branch conditions
stage('PR Validation') {
  when { changeRequest() }
  steps { sh 'mvn -B test' }
}

stage('Deploy to Test') {
  when { branch 'main' }
  steps { sh './deploy.sh testing' }
}

End-to-end delivery

DockerHub and Kubernetes

After build and test, package the application once, assign an immutable identity, publish it, and deploy that same artifact.

CheckoutKnown commit
BuildCompile/package
TestPublish reports
ScanQuality/security
ImageUnique tag
DeployVerify rollout

Dockerfile for a Java application

Dockerfile
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY target/my-app.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]

Build and push an immutable image

Jenkinsfile stages
environment {
  IMAGE_NAME = 'mydockerhubuser/my-app'
  IMAGE_TAG  = "${env.BUILD_NUMBER}-${env.GIT_COMMIT.take(7)}"
}

stage('Build Image') {
  steps {
    sh 'docker build -t $IMAGE_NAME:$IMAGE_TAG .'
  }
}

stage('Push Image') {
  steps {
    withCredentials([usernamePassword(
      credentialsId: 'dockerhub-creds',
      usernameVariable: 'DOCKER_USER',
      passwordVariable: 'DOCKER_PASS'
    )]) {
      sh '''
        set +x
        echo "$DOCKER_PASS" | docker login \
          -u "$DOCKER_USER" --password-stdin
        docker push "$IMAGE_NAME:$IMAGE_TAG"
      '''
    }
  }
}
✓
Use one immutable tag per build.

A build number plus short commit SHA is better than relying only on latest. Deploy the same image to test, staging, and production instead of rebuilding it for each environment.

Deploy and verify Kubernetes

Kubernetes stage
stage('Deploy to Kubernetes') {
  when { branch 'main' }
  steps {
    withCredentials([file(
      credentialsId: 'kubeconfig-test',
      variable: 'KUBECONFIG'
    )]) {
      sh '''
        kubectl set image deployment/my-app \
          my-app=$IMAGE_NAME:$IMAGE_TAG -n test

        kubectl rollout status deployment/my-app \
          -n test --timeout=180s
      '''
    }
  }
}
Helm deployment stage
Helm
stage('Deploy with Helm') {
  when { branch 'main' }
  steps {
    sh '''
      helm upgrade --install my-app ./helm/my-app \
        --namespace test --create-namespace \
        --set image.repository=$IMAGE_NAME \
        --set image.tag=$IMAGE_TAG \
        --wait --timeout 3m
    '''
  }
}

Debug systematically

Troubleshooting and results

Start with the symptom, reduce the scope, collect evidence, find the root cause, fix it, and prevent recurrence.

SUCCESS

All required stages passed and the expected outputs were produced.

FAILURE

A required build, test, scan, push, or deployment step failed.

UNSTABLE

The build completed but quality signals such as tests or warnings did not meet expectations.

First questions

One job or every job? One branch or every branch? One agent or every agent? What changed last? Always reproducible or flaky?
SymptomCheck firstTypical cause
Job stuck in queueQueue message, label, node status, free executorsLabel mismatch, offline agent, no executor
Execute shell seems to do nothingScroll below Add build step; refresh pageThe command box was added lower on the same page, or UI JavaScript failed
GitHub push does not trigger buildWebhook delivery, endpoint, job trigger, external reachabilityJenkins is localhost-only, wrong URL/event, proxy or TLS issue
Credential errorCredential ID, type, scope, expiryWrong ID, folder visibility, expired token
Docker push failsLogin, image name, tag, networkWrong registry credential or repository path
Kubernetes rollout failskubectl output, pod events, image pull, readinessBad kubeconfig, namespace permission, unavailable image, failing probe
Tests are flakyJUnit report, test timing, shared dataEnvironment dependency, race, poor isolation
High-value evidence to collect
  • Console Output and the exact failing command.
  • Stage duration and the first stage that changed behavior.
  • Agent logs, available disk, memory, tools, and permissions.
  • Webhook request/response and reverse-proxy logs.
  • JUnit, coverage, SonarQube, dependency, or image-scan reports.
  • Docker output, kubectl events, pod logs, and rollout status.

Quick check

A job says: “There are no nodes with the label ‘maven-docker’.” What should you inspect first?
